# Keyenv

Use an installed `keyenv`, or the explicitly selected repository build. Never use `keyenv-lab` for actual credentials; its fixture key is public.

Read `tools/keyenv/README.md` for this version's supported commands before operating. The current CLI does not provide a help command. Use `keys --offline`, `list` and `inspect` to identify fields and entries through metadata only. Resolve ambiguous names with the user. Never request, display, read back, or copy secret values into chat, command arguments, logs, or Git.

Sensitive input belongs in a local terminal controlled by the user. Explain the exact local window and prompt. Do not simulate typing passwords, verification codes, or credential values. Noninteractive refusal is a request for local user interaction, not permission to bypass it.

Setup asks for the master password once and saves a device-local unwrapped data key in the owner-private vault directory. The master password is never saved. Existing vaults use one explicit user-operated `unlock` to enable this cache; subsequent maintenance reads it without requesting the master password. Cached metadata, backup, and explicitly requested `run` operations can run without a terminal; adding or replacing secret values still needs the user's hidden input. Never read, display, copy, or upload `unlock-cache.json` or its temporary files. `LOCAL_UNLOCK_REQUIRED` requires the user's explicit terminal unlock. Do not lock a ready vault unless the user requests it. `lock` deletes the local cache; it does not revoke remote access or stop existing processes.

An entry name (for example, openbb) and its field names (environment variable names) are separate identifiers. Preserve user-selected field spelling, and ensure the target program consumes that name; metadata inspection never needs to expose the value. The user can enter classic K=V through hidden `set` prompts, with no service entry or field-count interview. New keys get independent encrypted revisions; existing grouped fields remain compatible. `keys` reports names only. Never pass assignments as command arguments. Submitted batches are encrypted locally before network writes; PENDING_ASSIGNMENTS means use sync without re-entering values. status/keys expose draft names/count only. Drafts are not active environment fields and are preserved by encrypted backup/restore. Changed parents require explicit handling; never overwrite a draft or discard it without the user's decision. discard-set requires personal confirmation and does not roll back already uploaded objects.

When the user authorizes global injection, `shell-install` adds a paths-only managed block to their chosen `.zprofile`, preserving existing text and a private backup. New login zsh shells load confirmed active local fields offline and define `keyenv` / `keyenv_load`; successful set/update/disable/resolve/sync through this function reloads the current shell. Existing other shells or GUI processes are not retroactively changed. Some agent executors do not inherit the profile; use an explicit `/bin/zsh -lc` when executing the target program and check only name-presence booleans, not values. Do not assume a GUI launch or a default shell is a login zsh. This user has explicitly requested this mode; use inherited environment directly without requiring a per-service run wrapper. Never call `env --offline --format zsh` to display its secret output, print environment dumps, or read private vault/cache files. Shell startup does not sync Drive or need Google login. For another user without this authorization, use `run` with an explicit entry and executable argument array. Values are literal environment variables; do not interpolate them into shell commands. Explain when existing variables will be replaced. Do not run unrelated programs or modify accounts. `export` creates plaintext and requires explicit user authorization for the destination.

For Drive setup, explain the target Google account and `drive.file` scope. Obtain action-time confirmation before creating OAuth credentials, accepting policies, or granting persistent access. The user personally completes authentication and verification. Do not retrieve verification messages. The formal CLI requests offline access with the existing client and drive.file, encrypts access/refresh tokens in device-local oauth-login.json, and refreshes automatically. Never inspect or copy this file or include it in backups, Drive, or Git. Lab tokens stay process-only. AUTH_REQUIRED after refresh needs user-operated login --reauthorize; do not silently delete cached grants, expand scopes, rebuild clients, or repeat authorization. logout removes only local encrypted login material, not the Google grant. lock removes the data-key cache, leaving encrypted login data unusable until unlock.

Treat pending writes, conflicts, disabled entries, corrupted caches, and unavailable authentication as explicit states. Never choose a conflict winner automatically. Offline cache reads cannot establish freshness. Preserve encrypted backups and local modifications. Do not push, publish, revoke credentials, or install globally without authorization.

This is a portable skill source, not proof of native plugin registration or completed real-account acceptance.

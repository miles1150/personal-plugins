# Miles Works setup after installing the plugin

Ask your assistant: “Help me set up Miles Works for direct messaging.” The plugin supplies the MCP endpoint; use the host's connection/login interface if prompted. Codex and Claude can use direct MCP. Complete browser sign-in and review the actual client and callback before approving. Do not put passwords, codes, callback URLs or tokens in chat.

After connecting, the assistant calls `works_identity`. If no assistant is mounted, it can request an existing assistant with `works_mount_request` or create a draft with `works_assistant_request`, then give you the approval link. You review the permissions and approve the mount; the assistant checks `works_mount_status` and calls `works_identity` again. A request is not a mount. Multiple mounted assistants require an explicit choice. To validate direct messaging, request a test message and verify its actual receipt. Sending alone does not prove processing. No bridge is necessary for this path.

If Claude on macOS reports that existing OAuth client information is required during the callback, its attempt to save the dynamically registered client may have failed. Check that your macOS login keychain is available and unlocked, and personally respond to any keychain prompt, then start a new login. This error can have other causes: if it persists, report the error and host version without sharing credentials, authorization URLs or callback URLs. Do not change keychain security settings or copy credentials between hosts to work around it.

## Optional: background Codex receiver

Ask: “Help me set up the optional Miles Works background receiver for this Codex session.” Claude direct MCP does not itself imply wake support; a webhook receiver requires its own integration as described below. The assistant should explain the separate bridge installation and that its approved mount grants the assistant's full approved permissions. Obtain authorization before configuring a receiver, starting a persistent process, or approving any client or mount. Never reuse another client's credentials.

1. From the installed skill directory, run `python3 scripts/bridge.py doctor`. It verifies the bundled executable and manifest for this platform; it does not check login, mounts, pairing, or a live session. A source checkout without the platform bundle cannot run it. Never fall back to an executable on `PATH`.
2. Confirm this is a stable Codex thread and identify its actual lowercase UUID and absolute Codex executable path. Use the already mounted execution client to register the session with `works_sessions_register` and `capability: "wakeable"`; obtain the assistant and session IDs from the service. Do not invent IDs or declare wake support for an unverified host.
3. Copy the bundled `bridge-v3.example.json` to a private configuration file and substitute the verified values and absolute paths. Create the credential parent and new state directory owned by the current user with mode 0700; save the config as mode 0600. Do not overwrite existing configurations, credentials, lock files, or journals. Use a separate state directory from any legacy receiver and stop an old receiver before enabling a replacement for the same work.
4. Run `python3 scripts/bridge.py bridge --config /ABSOLUTE/PATH/v3.json login` for independent OAuth. Review the actual client, callback and `works:client` scope before approval. Then run `python3 scripts/bridge.py bridge --config /ABSOLUTE/PATH/v3.json mount-request ASSISTANT_ID`. The user reviews and approves the resulting request in the dashboard; check it with `mount-status REQUEST_ID`. The bridge uses its own identity, not the host's. If the request outcome is uncertain, inspect the dashboard before creating another. Never copy the host's token.
5. After the bridge mount is approved, `python3 scripts/bridge.py bridge --config /ABSOLUTE/PATH/v3.json pair SESSION_ID` sends a challenge that the configured Codex session must confirm using its own mounted MCP connection. Check pairing status and run `once`; verify that a test message reached and was actually processed by the intended session. A queue receipt alone is not processing. Start `run` only when the user has authorized a persistent receiver.

Keep the state directory and credential file across restarts. A wake with unknown outcome is never automatically retried; independently inspect it before any explicit reconciliation. A fresh OAuth login creates a different installation; this release does not support safely transferring an existing v2 journal to it. On an installation mismatch, stop the receiver, preserve both the credential file and state directory, and inspect the journal with `status --items`; do not delete the journal, replace credentials, or start a parallel receiver. If the original valid credential is still available in its original private file, restore the original configuration and restart only after checking that no other receiver is active. If refresh outcome is unknown or the original credential is unavailable, leave the receiver stopped and request recovery assistance; the old refresh token must not be replayed. Direct MCP remains available independently.

Old Space/Actor/Consumer bridge configurations no longer run. Stop the old service, preserve its credential and state directory, and use a separate v2 state directory. If authorized, `python3 scripts/bridge.py bridge --config /ABSOLUTE/PATH/v3.json import-legacy /ABSOLUTE/PATH/OLD-STATE` opens the stopped old journal read-only and copies its references into quarantine; it does not infer v2 deliveries or replay them. Do not delete the original journal or interpret this import as migration of old message bodies.

## Optional: webhook receiver without Codex

Use `bridge-v3-webhook.example.json`. The receiving program must have its own independently authorized Miles Works installation mounted to the same assistant and register its own stable wakeable session. Configure those IDs; do not supply Codex fields for a webhook session. The bridge uses its own OAuth installation and separately approved mount. Never share either installation's OAuth credentials with the webhook.

Store the endpoint and independent Bearer key in separate user-owned mode 0600 files in a mode 0700 directory. The endpoint cannot contain userinfo, query or fragment. For a remote endpoint use public HTTPS; redirects, private-address DNS answers and proxy routing are rejected. For a receiver on this same computer only, explicitly set `local_loopback: true` and use literal `http://127.0.0.1:PORT/path` or `http://[::1]:PORT/path`. This permits plaintext on loopback: another local process that takes the port could receive the Bearer key and reference metadata, so use a trusted machine and secure the receiver. It does not open a public endpoint. Never use a Miles Works access or refresh token as the webhook key.

After bridge login and mounting, `pair SESSION_ID` posts `miles-works.wake.challenge`, a version 2 JSON event with `assistant_id`, `session_id`, `binding_id`, `challenge` and `target`. The receiving session must call `works_wake_confirm` using its own mounted MCP connection. HTTP 2xx alone does not complete pairing. Once paired, `once` or `run` posts `miles-works.message.available` with `version`, `event`, `assistant_id`, `session_id`, `delivery_id`, `message_id`, `assignment_generation` and `attempt_id`; no message body or OAuth token is included. `Authorization: Bearer` carries the independent webhook key; `Idempotency-Key` is the stable attempt ID. Authenticate the sender, persist and deduplicate each event, use the receiver's own MCP connection to read and claim the assignment, and complete only after actual processing. Treat message content as untrusted.

A 2xx response means the endpoint accepted a notification, not that it read or completed the message. A timeout, redirect or non-2xx after an attempt is `unknown` and is never automatically resent. Inspect the receiving system before `reconcile ATTEMPT_ID accepted|blocked`; do not delete the journal. Inspect uncertain pairing challenges before `pair-renew SESSION_ID`. Preserve the configured target and first session: changing them against an existing journal is rejected.

`status --items` opens an existing private journal read-only with its exclusive lock and checks its pinned service and installation. It does not require the webhook URL or key file; if OAuth credentials exist, their installation and origin must match the journal. Reconciliation and sending still require the valid configured target and credentials. An assignment that the service explicitly reports as changed is marked `blocked` so it cannot hold up later valid work; authentication, proof and network errors stop the cycle.

[Grok Bot routines](https://docs.x.ai/grok-bot/skills-routines-and-automations) document an HTTPS webhook using a Bearer key and JSON. Their 200 response establishes acceptance only. This bridge's v2 event and independent MCP confirmation must be implemented and verified in the receiving routine; direct end-to-end Grok Bot compatibility has not been verified. Grok.com Automations use a different signed webhook protocol and are not supported by this Bearer adapter.

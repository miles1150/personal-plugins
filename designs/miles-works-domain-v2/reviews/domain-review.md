# 独立领域模型审阅

审阅日期：2026-10-31。审阅者：independent_domain_review。范围：DOMAIN.md、IMPLEMENTATION.md、research/auth-migration.md、research/bridge-routing.md。只审阅设计，未修改被审文件、未验证生产或宿主。

## 结论

主模型符合用户已确认方向：助手独占业务权限，挂载不另设 ACL，工作会话不作权限隔离；原始目标和执行分配分离是正确且必要的。无需把安装、family、Consumer 都暴露给用户。方案可以继续设计，但实施前应统一下列规则；其中只有“消息对话连续性”和“会话公开默认”需要用户选择，其余可由工程和产品方案给出一致默认。

## 按严重性排序

### 高：同一消息对话的并发处理没有统一定义

位置：DOMAIN §6 路由表、§6.1、§6.2；bridge-routing「普通发送」。

主文路由表说助手目标始终走默认；§6.1 又建议已有对话走原负责人。主文说显式指定只改变本条；研究说原工作执行中应待转交。当前 claim 唯一性仅在 delivery 层，两条不同消息可分别被两个会话同时领取，因此不能凭该 claim 宣称“同一对话只有一个负责会话”。

建议：先让用户确认旧对话跟随原会话还是每条独立路由。若选择连续性，定义 `(conversation_id, recipient_assistant_id)` 的负责人及 execution generation；显式改投另一会话时保留消息，但对话有进行中任务则进入待交接，不能自动并发执行。无需引入全局任务引擎；可先用一张对话负责人记录与 CAS。若选择每条独立，删除“一段对话唯一负责会话”的承诺并明确上下文分叉。

### 高：撤销挂载/暂停会话之后，默认引用和待处理任务如何恢复缺项

位置：DOMAIN §2 默认引用约束、§5 生命周期、§6 删除规则、§9 不变量；IMPLEMENTATION 数据表。

默认要求挂载有效，但只定义了删除默认会话的原子替换。撤销其客户端挂载、禁用安装、暂停工作会话，同样会留下不可投递的默认；不能把它当普通离线继续等待。

建议：在挂载撤销/实例禁用事务中使其会话不可新接收并更新路由版本；是否替换遵循同一明确规则，缺候选则默认空。暂停会话可以保留“用户选择的默认”，但必须另有有效路由状态并显示暂停等待；或直接采用同样替换规则。主文应选一种。已领取/unknown 保持待核查，不自动重跑。这是模型闭包问题，可自主选一致默认，不必再问用户“是否应拒绝已撤销客户端”。

### 中：注册/会话管理的自动化边界与“助手管理必须人类操作”冲突

位置：DOMAIN §4.2「助手管理…是人类控制面操作」；IMPLEMENTATION §3 sessions_register/list/update。

用户希望使用时注册会话、让 Agent 使用工具。若“助手管理”含注册/改默认/发布/删注册，每次都需网页会削弱这一目标；若 Agent 可自助改这些字段，应明确不是获取新的业务权限。

建议：人类确认边界只列助手业务政策提升、新客户端挂载及账户安全管理；已挂载客户端可在其助手范围注册自身会话、更新能力/心跳，删除自身注册。改默认/发布可作为已有消息能力下的工作配置执行，但要保存审计并展示影响。若想逐次询问默认切换，应单独说明为产品确认而非新 ACL。

### 中：默认替补算法及历史积压处理在文档间不一致

位置：DOMAIN §6 与 bridge-routing「删除默认会话」「普通发送」。

主文候选优先在线/可唤醒，研究优先预设替补/最近成功接收；主文把旧未完成统一待交接，研究允许未开始且助手级目标自动重分配；积压自动接管在主文的语气强于研究的待确认。

建议：主方案选一个确定算法，研究保留为被评估选项并注明最终采用项。建议删除确认预选最近成功接收的有效会话，允许修改；没有成功记录按注册时间稳定选择；不要求用户维护额外优先级表。设置默认页面带默认勾选“接管 N 条未分配消息”，明确排除显式目标/已领取/unknown，使行为可审阅且不必新增高负担问答。

### 中：会话“删除”需限定为注册解绑，不应顺带删除宿主 thread

位置：DOMAIN §5、§6、§8；原型会话删除文案需同步。

文档明确软删除服务端记录，但用户看到“删除会话”可能理解 Codex 对话本身被删除。宿主 thread 已归档/关闭/真实删除也不一定能可靠自动检测。

建议 UI 使用“移除工作会话”，说明只停止 Miles Works 接收与目录展示，保留宿主历史；宿主侧删除被检测到后执行同一注册失效流程，能力不支持检测时显示“目标不可用，需修复”，不能声称自动识别删除。

### 低：实体表可拆为用户概念和实现记录，避免重新制造认知负担

位置：DOMAIN §2。

13 行实体对技术方案有用，但面向用户的模型图只需账户→助手→客户端/工作会话，消息进入收件箱。Policy、Attachment、family、Delivery、Consumer、Space 放实现映射附表；“独立实体”不意味着独立导航入口或设置页。

## 仅保留真正需要用户决定的问题

1. **对话连续性：**同一段往来不指定会话时继续原会话，还是随当前默认变化？推荐继续原会话。显式改投在原任务执行中时推荐待交接，不自动并行。
2. **会话目录默认：**主动注册会话时是否默认在同账户其他助手的收件人中展示？推荐注册表单明确默认开启的开关；不把所有宿主 thread 自动注册/公开。
3. **密钥资源范围：**全部现有和未来密钥，还是指定集合？这不是重复询问读/写/新建；用户已确认这三项能力，资源范围仍应清楚披露。可采用全量推荐值并给高级范围。

无需重新询问：助手是否存在、是否多客户端、是否每 thread 隔离、是否另设连接权限、无默认是否积压、删除默认是否替换。这些用户已经确认。

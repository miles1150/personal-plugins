## P1：领域行为或核心旅程

### U1. 研究助手挂载/积压恢复会串到开发助手

位置：`app.jsx` 的 connect 注册入口、sessions 页面、inbox 的“管理接收位置”；sessions/defaultId 为全局状态，实际仅服务开发助手。

路径：给“研究助手”发送无默认消息 → 等待分配 → 管理接收位置 → 显示“开发助手”；或挂载研究助手 → 查看会话注册 → 新会话登记到开发助手。研究助手的等待消息没有可完成的恢复路径。`DESIGN.md` 已诚实说明此限制，但与用户本轮要求的完整交互旅程仍有差距。

建议：以 assistant_id 保存 sessions/default/mounts，管理入口传入所属助手；至少研究和新建助手可完成“挂载→注册→默认→积压分配”。不要把错误助手页面当占位功能。

### U2. 删除会话会把已完成任务重新标成待交接

位置：`removeSession` 对所有 `m.assigned===deleteId` 都重写 state、清空 assigned。

路径：发消息 → 模拟领取 → 模拟完成 → 删除该会话。已处理记录变成 handoff/target-deleted，丢失实际执行归属，与“消息与历史保留”“不自动重跑”冲突。

建议：终态记录保留完成状态和历史会话 ID/显示名快照；会话墓碑可显示“原会话已删除”。只有未完成任务进入交接流程，并区分明确未执行和执行结果未知。

### U3. 新建助手的权限不是独立快照

位置：单个 `created` 字符串加全局 `permissions` 状态；created 卡片和挂载确认均读当前编辑器权限。

路径：创建助手 A → 再开创建页改勾选但取消 → A 的权限展示已经变化；再创建助手 B 会覆盖 A。

建议：助手对象持有创建时 policy snapshot，创建表单使用独立草稿；取消不改变已创建助手。若只做单助手样本，需禁用第二次创建并明确边界，但建议完成真实多助手演示。

### U4. 挂载撤销、助手权限修改和 bridge 结果未知尚无可审阅路径

位置：`DESIGN.md` “尚未落入原型的生产合同”；bridge 页面只有推进成功/暂停/身份不一致。

这些是新模型的重要体验：一个助手的政策影响所有客户端；解绑不删助手数据；通知响应丢失不应再次唤醒。仅用说明文字无法审阅操作时如何向用户表达后果。

建议：增加最小可交互状态：编辑助手权限→影响客户端摘要；解除挂载→会话和默认影响；bridge unknown→核对通知状态→等待/确认恢复，不提供无条件“重试执行”。无需模拟真实安全机制。

## P2：清晰度与提案一致性

### U5. 删除默认确认没有展示实际替代者

当前确认只说“将替换为其他可接收会话”，实际实现选择在线优先/列表首项。用户无法在确认前知道任务以后落在哪台机器/哪个会话。

建议：展示具体替代会话、客户端、在线/主动查收状态，以及没有候选的空默认说明；候选排序无需让用户理解算法。

### U6. 登录页把协议研究误写成必需的宿主 token 升级

当前文案称“登录后再挂载需要宿主凭据升级／重新授权支持”；主技术方案推荐固定协议 scope、服务器在线挂载，不应预先断言必需 token exchange。

建议：产品页只说“登录后可以创建助手或连接已有助手”；技术依赖移到设计说明，准确写“固定凭据下动态挂载与工具调用仍待宿主验证”。同页“客户端自报名称/设备未验证”可缩成可展开详情，避免普通登录界面重新承载研究解释。

### U7. 对外展示范围及默认值需要一句可读定义

“在其他助手的收件人列表中展示”不明确是同账户还是跨账户。原型新会话默认关闭、旧样本开启，设计说明有待定标识；可以作为探索，但不应称已确定默认。

建议首版文案“在我的其他助手的收件人列表中显示”，跨账户另行设计；发布开关与收件权限不可混为一谈。

## 正面检查

- 用户可不设默认；默认清空不会搬走已分配任务。
- 显式目标已删除的新发送会拒绝，不静默走默认。
- 临时离线不会自动换默认。
- 权限复选框位于助手创建，挂载页只说明继承，未重复建连接权限。
- 中英文切换覆盖主要操作与状态；本轮未声称完整键盘/读屏器验收，视觉/可访问性由设计 Agent 的实际验证记录补充。
- bridge 分开描述通知、领取、完成，明确不证明外部结果成功。

## 应问用户的少量问题

1. 注册会话后是否默认展示给账户内其他助手？这是可发现性默认，不是安全权限。
2. 设置默认会话后是否自动接管此前无默认的未分配积压？推荐自动，仅未指定/未开始记录。
3. 已有对话后续未指定会话时是否继续原负责会话？推荐继续，以保留上下文。

密钥范围由主任务统一问，避免重复。删除确认展示具体替补、历史保留、状态不串助手、表单草稿隔离、技术说明移出主流程均是工程/设计可自行解决的问题，不应转嫁用户。

### 保留的原型限制

- 仅保留一个新增助手示例，第二次创建会替换该示例。DESIGN.md 已明确，不应称为任意数量助手管理实现。
- 解绑状态仅对开发助手/Codex 的接收演示完整生效；会话候选、注册、收件箱“模拟领取”尚不是统一权限状态机，不能用它验证撤销后的实际 API 拒绝或默认路由候选排除。生产实现必须遵循主方案的 active mount 检查。
- 完成消息保留原会话 ID，但会话删除后展示通用“已删除会话”，尚未保留可读的历史会话名称快照。
- 对话连续性、会话发布默认、默认候选排序仍是待确认设计分支；此原型偏重新消息分配，不演示完整跨宿主上下文交接。
- 仅本地合成交互；未验证 Google、实际宿主、D1 事务、私有凭据或真实 bridge。未发现需要阻止本轮方案讨论的剩余 P0；上述限制必须随交付保留。

## 末次静态复核：解绑与默认候选联动

设计 Agent 进一步修复后，按主任务要求仅静态复核 app.jsx，不重复运行大测试矩阵。以下结论覆盖并取代上一节“解绑仅挡 bridge 演示”的旧限制：

- 开发助手解除 Codex 挂载会把该客户端会话标为不可接收；默认会话改为其他有效候选或空；未完成分配转为待交接，done 历史保留。
- 默认选择、显式收件人、交接候选均排除不可接收会话；被解绑实例注册按钮和该会话的模拟领取/完成入口被禁用；bridge 继续阻止唤醒。
- 移除默认会话前可查看替补的名称、客户端、在线状态及后台唤醒/主动查收能力，并可以改选或留空。保存时重新核实候选有效性。
- 操作文案改为“移除会话”，确认明确只移除 Miles Works 注册，不删除宿主原始对话。

这些补充使解绑与路由的主要产品后果可审阅，不再是只切一个 bridge 状态。仍保留的限制是：演示以开发助手 Codex 挂载为具体样本，不是任意客户端/助手的完整服务端状态机；能力来自样本数据而非真实宿主探测；一个新增助手样本、历史名称快照、完整对话连续性和真实 OAuth/bridge/D1 验收仍未实现。设计 Agent 正进行针对性验证，其结果应另据实际记录引用。

两项轻量实现提醒（不扩展本轮范围）：

2. 挂载后的“客户端自动登记工作会话”是目标能力，生产上线时需依据宿主能力呈现；不支持可靠会话 ID 的 MCP 客户端仍应走主方案的主动查收降级，不能由这句原型文案推定已验证。

上述提醒和此前明确的样本/真实服务限制继续有效；除此之外，本轮 UI 收敛可以交付用户审阅。

# Bridge / 路由独立审阅

审阅者：bridge_research。2026-10-31。仅静态阅读 DOMAIN.md、IMPLEMENTATION.md 和 prototype/index.html 引用的 app.jsx；未运行浏览器，不声称交互测试通过。以下只列具体问题，未自行修改主稿。

## BR-1 高：同一消息对话跨会话执行的并发规则没有落到领取约束

位置：DOMAIN.md:117、123；IMPLEMENTATION.md:41-42、77。

场景：消息 M1 已由会话 A 领取；同一 conversation 的后续 M2 显式指定会话 B。现稿说“显式目标仅改变本条”，claim 唯一键却只到 delivery。A、B 可以同时持有不同 delivery 的有效租约，因此“对话跨会话冲突可见而非静默并发”的验收条件没有实现模型支持。

建议：先把此处列为用户决策，不默认发明串行策略。若采用“一段对话同一时刻只有一个工作会话执行”，补 `(assistant_id, conversation_id)` 的执行所有权/版本及冲突状态；B 的显式目标仍保留，但等待交接，不改投 A。若允许对话内分支并行，就明确 task/branch 的分组边界，不把 delivery claim 描述为整个任务唯一执行者。

## BR-2 高：原型删除会话会把已经完成的消息改成待交接

位置：prototype/app.jsx `removeSession`（第 13 行附近，文件压缩行）。

该函数对所有 `m.assigned===deleteId` 的消息改为 handoff/target-deleted，没有排除 `done`。操作路径：发送→领取→完成→删除负责会话；“已处理”历史会重新变成待交接，与“删除保留执行历史”冲突，也可能误导用户重跑。

建议：completed 为终态，删除后保留原 assigned_session_id 的墓碑引用、显示已删除名称；只对未终结且确实需要交接的记录转换状态。保持原始目标和已完成回执不变。

## BR-3 中：bridge 运行环境与 Codex 客户端实例仍被一个 installation_id 混用

位置：DOMAIN.md 实体表 Installation；第 129-137 行；IMPLEMENTATION.md:35-38；原型后台接收卡“Mac mini · Codex”。

现稿将 Installation 定义为带 host_kind 的客户端实例，但又让“一台安装环境一个 bridge”拉“分配到本实例”的多宿主工作。独立 bridge OAuth 所在实例和 Codex/Claude 接收会话所在实例并不必相同，按同一 installation_id 查询会遗漏或错绑。

建议：不必新增用户可见实体，但技术上区分 `bridge_instance_id` 与会话的 `client_instance_id`，用已登记的 `session_wake_binding` 明确桥接实例能唤醒哪些会话。receiver proof 同时包含双方实例、助手和会话 revision，不能要求二者 ID 相等。原型把 bridge 标成“Mac mini · 后台接收程序”，把 Codex 放到它的目标适配器/会话行。

## BR-4 中：默认替换在原型里已经跨客户端自动执行，但未展示具体替补

位置：DOMAIN.md:111；prototype/app.jsx `removeSession`、删除确认区域。

原型删除 Codex 默认会话，会自动选 Claude Code · MacBook（当前离线且仅主动查收）。确认区域只说“其他可接收会话”，未展示替代者及能力。正文要求“删除前显示将替换为谁”，并把跨客户端替换列为待确认，因此原型偷偷固化了一种未确认行为。

建议：删除确认页直接显示替代会话、客户端、离线/主动查收状态，并允许选其他候选或无默认；标注替补规则待确认。若选择无默认与用户“有候选就替换”的初衷冲突，以问题方式让用户决策，不自动扩大自由度。

## BR-5 中：恢复流程只有原则，没有可审阅的交互入口

位置：原型 Inbox handoff/target-deleted 卡、后台接收页面；DOMAIN.md:125、135。

原型的待交接卡只有“管理接收位置”，并无选择目标、查看已发生执行、确认转交的操作；后台接收也不能演示 unknown、租约过期与恢复，只能正向推进。用户无法据原型判断“不会重跑”在实际操作中如何成立。

建议：补一个共用恢复面板：原目标、现分配、最后证据、unknown原因、只读核查结果；提供“确认未执行后重新派送”“已有结果，记录完成/待复核”“转交并附摘要”，对没有证据的自动重试保持禁用。模拟操作明确标注，不能把按钮完成当真实验收。

## BR-6 中：研究助手积压消息的恢复导航进入开发助手会话

位置：prototype/app.jsx Inbox 卡的 `go('sessions')`；sessions 页面固定“开发助手”。

原型主动引导给研究助手发送以体验无默认积压，但该消息的“管理接收位置”却进入开发助手，会让用户设置错误助手的默认会话，且不能解决积压。

建议：会话页面用 selectedAssistant 上下文；在 Inbox 跳转时带消息收件助手，注册、默认选择和挂载均校验同一助手。至少不能在原型展示错误恢复路径。

## BR-7 低：路由总表与对话连续性段落条件冲突

位置：DOMAIN.md:101-102 vs 117；原型默认说明/发送预览。

总表和原型说“助手目标有默认走默认，无默认积压”，后文又说既有 conversation 优先原负责会话。因此清空默认后，旧对话的助手级消息究竟仍送旧会话，还是等待，当前文案给出两种结果。

建议：表格限定“新对话/无有效负责人”；增加既有对话一行。待用户确认连续性规则前，原型标清演示的是新消息对话。

## 应汇总给用户的路由问题

1. 同一消息对话未结束时显式发往另一会话，是交接、独立分支，还是允许同时处理？这一项决定模型，不是实现细节。
2. 默认会话删除后是否允许跨客户端/跨模型自动替补，包括只能主动查收的会话？候选展示可减少误解。
3. 设置默认后是否自动接管此前未分配积压？既有对话是否优先原负责人？现稿已有提案，应在 QUESTIONS.md 保持一致。

不需再问用户技术字段、锁粒度或 lease 秒数。当前 claim 续期缺口已在方案识别；fencing/unknown不重放的方向正确，但 BR-1 与 BR-3 应在开发前消除歧义。
